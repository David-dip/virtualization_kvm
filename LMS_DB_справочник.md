# LMS ИУБиП — справочник по базе данных `appiub95_lms`

Источник: дамп phpMyAdmin от 08.10.2026, MySQL 5.7.21 (Beget), Laravel (Jetstream + Livewire + spatie/permission).
Всего: **116 таблиц, 158 внешних ключей, ~3,3 млн строк**. Цифры «N строк» взяты из дампа.
Пометка «(вероятно)» — вывод по структуре и данным, а не по коду приложения: проверьте по моделям Laravel.

## 0. Как устроена БД (общая картина)

```
                         ┌───────────── справочники (страны, города, формы обучения, ...)
                         │
  users ─1:1─ users_data ┤            ┌── groups ── group_student ── users
    │                    │            │      │
    ├── user_status ─ statuses        │      └── work_study_plans ── work_study_plan_courses ── …_in_semesters
    │   (роль в вузе: студент,        │              │                                              │
    │    препод., абитуриент…)        │         study_plans (шаблон)                    …_control_types_in_semesters
    │                                 │                                                             │
    ├── order_user ── orders ─ order_types                                    bulletins (ведомости) ┘
    ├── student_state / students_academic_leaves                                    │
    ├── e_journals, schedules                                              student_grades (1,09 млн оценок)
    ├── student_document_order_requests/issuances (справки)                         │
    └── social_passports, student_family_statuses, my_publications, ...     student_retake_bulletins (пересдачи)
```

Ключевые идеи:

1. **Центр — `users`.** Почти все таблицы ссылаются на `users.id` (студенты, преподаватели, абитуриенты, сотрудники — в одной таблице). ФИО, паспорт и т.п. вынесены в `users_data` (1:1).
2. **Кто ты в вузе — это `user_status`** (студент / преподаватель / абитуриент / выпускник…), а **права в системе — это spatie-роли и permissions**. Это две независимые системы.
3. **Много таблиц синхронизируются с внешней системой** (вероятно, 1С/«Университет»): у них есть `external_id`. Это справочники, планы, группы, приказы, ведомости, оценки.
4. **Живые «веб-функции» LMS** (электронный журнал, справки, соцпаспорт, наука, воспитательная работа, оперативная деятельность, решения ректората) — без `external_id`, их данные создаются прямо в LMS.
5. **Учебный план в двух экземплярах:** `study_plans` (утверждённый учебный план) и `work_study_plans` (рабочий учебный план, РУП, на конкретный филиал/группу). Структура у них зеркальная.

## 1. Пользователи, доступ, роли

### `users` — 31 873 строки
**Про что:** единая учётная запись всех: студенты, абитуриенты, преподаватели, сотрудники.
**Поля:** `name` (фактически **логин**: числовой номер, например `1536462`, или `st113804`), `email`, `password`, поля Jetstream (`two_factor_*`, `current_team_id`, `profile_photo_path`), `deleted_at`.
**Что в данных:**
- `email` заполнен только у **27** пользователей (то есть вход, судя по всему, по логину `name`).
- `password` пуст у **23 263** (те же, у кого `name` — число): записи импортированы без пароля.
- Форматы хэшей **смешанные**: `$2y$` (bcrypt) — 4 440, `$6$` (SHA-512 crypt, «чужой» формат) — 4 167, `$2a$` — 1, и **2 значения, похожие на нехэшированный текст** (начинаются с `rest…`).
- `two_factor_*`, `current_team_id`, `profile_photo_path`, `email_verified_at`, `remember_token`, `deleted_at` — **не используются нигде** (везде NULL).
**Связи:** на неё ссылаются 39 таблиц.
**Как использовать:** это «точка входа» любого запроса; ФИО брать из `users_data`, а не из `users.name`.
**Улучшения:**
- Вынести логин в явную колонку `login` (UNIQUE), `name` оставить под отображаемое имя (сейчас `users.name` вводит в заблуждение).
- Перехэшировать/сбросить пароли в нестандартных форматах (`$6$…`, `rest…`) — при входе делать rehash на bcrypt/argon2.
- Удалить неиспользуемые поля Jetstream (или включить 2FA).
- Добавить индексы/уникальность по `name` (логин) — сейчас в таблице только PK.

### `users_data` — 31 873 строки (1:1 с `users`)
**Про что:** персональные данные: ФИО (+ родительный/дательный падежи для справок), дата рождения, пол, паспорт, СНИЛС, ИНН, семейное положение, гражданство, филиал.
**Связи:** `user_id → users`, `document_id → documents` (тип документа), `family_status_id → family_statuses`, `branch_id → branches`; синхронизация: `external_user_id`, `external_user_data_id`.
**Что в данных:**
- Связь 1:1 **держится только договорённостью**: на `user_id` нет UNIQUE.
- `inn` пуст у **100%**, `birthplace` пуст у **100%** — колонки не используются.
- `snils` пуст у 22 259; **479 повторяющихся СНИЛС** (потенциальные дубли людей).
- `country` и `citizenship` — **одинаковые по значениям** (одна и та же колонка продублирована); обе целые, **без FK** на `countries`.
- Дублируется «мягкое удаление»: `is_deleted=1` у 2 121 человека, при том что `deleted_at` нигде не заполняется.
- ~205 подозрительных дат рождения (раньше 1930 или позже 2012).
- Паспортные данные, СНИЛС хранятся **открытым текстом**.
**Улучшения:** UNIQUE(`user_id`); FK `country`/`citizenship` → `countries`; оставить одну колонку гражданства; выбрать один механизм soft delete; проверка формата СНИЛС (11 цифр + контрольная сумма) и UNIQUE; шифрование паспорта/СНИЛС (`Crypt`/`encrypted` cast) или вынос в отдельную таблицу с ограниченным доступом; индекс по (`last_name`,`first_name`,`middle_name`) для поиска.

### `user_status` — 57 687 строк
**Про что:** «роль человека в вузе» (многие-ко-многим `users` × `statuses`) + к чему привязан: специальность (для студента) или должность в подразделении (для сотрудника).
**Связи:** `user_id → users`, `status_id → statuses`, `speciality_id → specialities`, `department_position_id → department_position`.
**Распределение:** Студент 27 710, Абитуриент 18 881, Выпускник 7 152, Преподаватель 2 130, Слушатель доп. обр. 759, Сотрудник 754, Аспирант 242, прочие единицы.
**Что в данных:** у 19 153 пользователей несколько строк (абитуриент → студент → выпускник, это нормально), но есть **1 201 точных дубликатов** (user+status+speciality+position); у 32 пользователей нет ни одного статуса. `speciality_id` и `department_position_id` оба `NOT NULL`, хотя по смыслу взаимоисключающие (студент — специальность, сотрудник — должность).
**Улучшения:** UNIQUE(`user_id`,`status_id`,`speciality_id`,`department_position_id`) после очистки дублей; сделать оба поля nullable (или разнести на две таблицы: обучающиеся / сотрудники); добавить `valid_from/valid_to` и флаг «текущий», чтобы не вычислять актуальный статус по последней строке.

### `statuses` — 18 строк
Справочник: Заведующий кафедрой, Библиотекарь, Студент, Преподаватель, Администратор, Руководитель образовательного проекта, Гостевой, Абитуриент, Ректор, **`m`** (мусорное название, id=10), Методист приёмной комиссии, Сотрудник, Слушатель доп. образования, Сотрудник ЦВиРИТ, Выпускник, Тренер, Аспирант, Докторант.
**Улучшение:** переименовать/удалить запись `m`; добавить `code` (например `student`) и ссылаться в коде по коду, а не по id.

### `roles` (3), `permissions` (46), `role_has_permissions` (1), `model_has_roles` (8 610), `model_has_permissions` (603)
**Про что:** spatie/laravel-permission. Роли: `Admin`, `Teacher`, `Student`. Permissions — крупные «доступы к разделам»: `access-to-contingent`, `access-to-e-journal`, `access-to-spt`, `access-to-student-grades`, `manage-student-document-requests`, `access-to-student-requests-for-certificates-{full|spo|vo}`, `rector` и т.д.
**Что в данных:**
- `model_has_roles`: Student — 8 274, Teacher — 336, **Admin — 0 назначений**.
- `role_has_permissions`: **одна** строка (Teacher ← `access-to-academic-workload`).
- Все остальные права (603 записи) выданы **напрямую пользователям** через `model_has_permissions`.
**Как использовать:** в Blade/Livewire — `@can('access-to-science')`.
**Улучшения:** собрать «пакеты прав» в роли (Приёмная комиссия, Деканат, Учебный отдел, Методист СПО, Методист ВО…) и назначать роли, а не 600 отдельных прав — проще аудит и выдача; решить, нужна ли роль `Admin`; роль `Student` (8 274) не соответствует 25 041 «студентам» в `user_status` — выровнять.

### `sessions` (43), `password_reset_tokens`, `personal_access_tokens`, `failed_jobs`, `jobs` (0), `job_statuses` (6), `migrations` (116)
Служебные таблицы Laravel. `sessions` хранит `ip_address`, `user_agent`, `payload`. `job_statuses` — собственная таблица статуса фоновых задач (6 записей `generate_spt_groups`, создаются кнопкой формирования групп СПТ). **Улучшения:** чистка `sessions` по cron (`session:prune`/lottery), для `job_statuses` добавить индекс по `job_uuid` и поле ошибки.

### `active_users` — 27 строк
Что-то вроде «пары/группы одновременных учётных записей»: `user_id` + JSON `list_user_id` (`{"id":[2190,20257]}`) — вероятно, переключение между несколькими аккаунтами одного человека (дубли учётки). **Улучшение:** вместо JSON — нормальная таблица связей `user_id → linked_user_id`, чтобы работали FK и JOIN.

## 3. Учебные планы и дисциплины

Эта часть — самая «тяжёлая» по схеме: у плана **два зеркальных набора таблиц**.

| Уровень | Учебный план (шаблон) | Рабочий учебный план (РУП) |
|---|---|---|
| Шапка | `study_plans` (611) | `work_study_plans` (1 252) |
| Семестры (число недель) | `study_plan_semesters` (6 576) | `work_study_plan_semesters` (11 319) |
| Дисциплины плана | `study_plan_courses` (42 725) | `work_study_plan_courses` (57 059) |
| Нагрузка по семестрам | `study_plan_courses_in_semesters` (63 330) | `work_study_plan_courses_in_semesters` (82 319) |
| Формы контроля в семестре | `study_plan_course_control_types_in_semesters` (64 954) | `work_study_plan_course_control_types_in_semesters` (84 433) |

### `study_plans` / `work_study_plans`
**Про что:** `study_plans` — документ учебного плана (специальность, форма обучения, уровень, квалификация, срок: семестры/годы/месяцы, даты создания и утверждения). `work_study_plans` — РУП на филиал (`branch_id`), ссылка `study_plan_id` на «родителя».
**Связи:** → `specialities`, `teaching_forms`, `level_educations`, `qualifications`, `branches`; `groups` ссылается **и на `study_plan_id`, и на `work_study_plan_id`**.
**Замечание:** `work_study_plans.study_plan_id` — **без внешнего ключа** (в данных все 1 252 значения валидны, ограничение поставить безопасно). Согласованность `groups.study_plan_id` ↔ `groups.work_study_plan_id` не защищена.

### `*_semesters`
Номер семестра и количество недель.

### `*_courses`
Строка плана = дисциплина (`discipline_id → disciplines`) + её индекс (`index_id`, `under_index_id`, `number_index` — например «Б1.О.05»), раздел (`section_id`).

### `*_courses_in_semesters`
Нагрузка дисциплины в конкретном семестре: лекции/практики/лабораторные/самостоятельная работа, часы, зачётные единицы, недели, часы курсовой, консультации, контроль и т.д. Это основа для расчёта нагрузки и отчётов по часам.

### `*_course_control_types_in_semesters`
Какие виды контроля есть у дисциплины в семестре (экзамен, зачёт, курсовая…). **К этой таблице привязаны ведомости** (`bulletins.work_study_plan_course_control_types_in_semesters_id`) и протоколы пересдач.

### `disciplines` — 3 538 строк
Справочник дисциплин (`name`, `short_name` до 1500 символов). **167 названий повторяются** (с учётом регистра/пробелов) — разные записи одной дисциплины из-за разных `external_id`.

### `chair_discipline` — 12 116 строк
«Кафедра × дисциплина × учебный год × семестр» — какая кафедра ведёт дисциплину. Основа для расчёта учебной нагрузки.

**Улучшения для блока планов**
1. **Слить зеркальные таблицы.** Вместо 10 таблиц — 5, с признаком `plan_kind` (`template`/`working`) либо одна иерархия «план → родительский план». Сейчас любая новая колонка нагрузки добавляется дважды, а выборки требуют `UNION`.
2. FK `work_study_plans.study_plan_id → study_plans.id`.
3. UNIQUE-индексы: (`plan_id`,`semester_number`) в `*_semesters`; (`course_id`,`semester_number`) в `*_courses_in_semesters`; (`courses_in_semester_id`,`control_type_id`) в `*_control_types_in_semesters`.
4. `credits` — `int`; зачётные единицы бывают дробными (1,5) — перейти на `decimal(5,2)`. `work_content_first/second` — `double`, лучше `decimal`.
5. `groups.study_plan_id` убрать (получается через `work_study_plan_id`) — иначе две правды.
6. Составной индекс `study_plan_courses(study_plan_id, discipline_id)` и такой же для РУП: именно по ним строятся отчёты.
7. Слить дубли в `disciplines` (с переносом ссылок) и добавить UNIQUE(`external_id`).

## 4. Группы, студенты, контингент

### `groups` — 2 815 строк
**Про что:** учебная группа: название, **курс** (`course`), год приёма (`year_admission`), год выпуска, РУП, план, филиал.
**Что в данных:** `course = 0` у 662 групп (нулевой/не заполнен); `year_completion` пуст у 1 543; **77 дублей** (название+филиал+год). По филиалам: Ростов 2 385, Донецк 211, Сальск 189, Невинномысск 30.

## 12. Сквозные рекомендации по схеме

### Целостность и безопасность данных
1. **Все 158 внешних ключей — `ON DELETE CASCADE`.** Это значит: удаление пользователя, дисциплины или группы **молча** сносит оценки, приказы, журнал, справки. Для «учебных» данных (оценки, ведомости, приказы, справки) лучше `RESTRICT` и мягкое удаление (`deleted_at` + глобальный scope).
2. **Нет UNIQUE** там, где по смыслу пара уникальна: `users_data.user_id`, `group_student(group_id,user_id)`, `student_grades(bulletin_id,user_id)`, `order_user(order_id,user_id)`, `user_status(...)`, `e_journals(...)`, `external_id` во всех синхронизируемых таблицах.
3. **Нет составных индексов** — только одиночные индексы FK, которые Laravel создаёт автоматически. Для отчётов нужны составные: `student_grades(user_id,bulletin_id)`, `bulletins(group_id,work_study_plan_course_control_types_in_semesters_id)`, `e_journals(group_id,lesson_date)`, `order_user(user_id)`, `user_status(user_id,status_id)`, `schedules(group,date)`.
4. **Недостающие FK:** `work_study_plans.study_plan_id`, `users_data.country`/`citizenship` → `countries`, `military_registration_students.user_id`, JSON-списки (`active_users`, `consultation_schedules.groups`, `video_conference_fallbacks.student_id`, `rectorate_and_council_decisions.operating_activity_id`, `social_passports.cohabitants`).

### Типы данных и «магические числа»
5. Десятки колонок `status`, `type`, `category`, `lesson_type`, `address_type`, `sex`, `document_type`, `type_protocol`, `grade` — **числа без справочника**. Завести PHP Enum (с `cases`) + `CHECK`/справочные таблицы, чтобы значения читались в SQL и отчётах (например, для `grade`: 1 — зачёт, 2…5 — оценки, 0/-2 — неявка/недопуск).
6. `varchar(255)` как значение по умолчанию → ужать там, где длина известна (`group_name`, `ticket`), и **не использовать `varchar(9216)`/`varchar(8000)`** в индексируемых местах.
7. `schedules` — привести `date`/`time` к `date`/`time`, добавить FK.
8. `credits`, `work_content_*`, `volume_*` — `decimal`, а не `int`/`double`.
9. Единый тип `external_id` (`bigint unsigned`, везде NOT NULL UNIQUE).

### Дублирование
10. Зеркальные таблицы планов (`study_*` / `work_study_*`).
11. Таблицы статистики приёмной кампании ×4.
12. Двойные источники: академ (`students_academic_leaves` ↔ `student_state`), решения ректората (2 таблицы), справки (старые 2 таблицы + новые 2), «страна/гражданство».
13. Копии ФИО в `social_passports`, `applicant_average_scores`, `student_document_order_issuances`: для справок (снимок на дату) это оправдано, для соцпаспорта и абитуриентов — нет.
14. Нумерованные колонки `previous_marriage_1…5`, `child_1…5` → строки.

### Инфраструктура
15. **MySQL 5.7 снят с поддержки (октябрь 2023)** — запланировать переход на MySQL 8.0 (CHECK, оконные функции, CTE, `utf8mb4_0900`), это упростит отчёты по студентам (ранг, накопительные итоги).
16. Включить **строгий режим** (в заголовке дампа `SQL_MODE = "NO_AUTO_VALUE_ON_ZERO"` — проверьте реальный `sql_mode` сервера; нужен `STRICT_TRANS_TABLES`), иначе в БД попадают даты вроде `1900-01-01`, `2918-…`.
17. Чистка `sessions` по расписанию; ротация `job_statuses`.
18. **Персональные данные:** дамп содержит паспорта, СНИЛС, соцпаспорта — не передавайте его третьим лицам и храните шифрованным; для разработки используйте обезличенную копию.

### План действий (по приоритету)
1. **Быстро и безопасно:** UNIQUE на `users_data.user_id`, `student_grades(bulletin_id,user_id)` (после чистки 28 дублей), составные индексы, FK `work_study_plans.study_plan_id`.
2. **Данные:** чистка дублей (`user_status`, `e_journals`, `orders`, `groups`, `disciplines`); исправление дат приказов; заполнение `academic_leave_start_date`.
3. **Безопасность:** rehash паролей, шифрование паспорта/СНИЛС, смена `CASCADE` → `RESTRICT` для учебных данных.
4. **Структура:** справочник оценок/статусов, нумерация справок через счётчик, `lessons` + `attendance` вместо `e_journals`.
5. **Рефакторинг (по возможности):** слияние зеркальных таблиц планов и таблиц статистики приёма, история студента (`group_student` с датами) вместо `student_state` + `students_academic_leaves`.
